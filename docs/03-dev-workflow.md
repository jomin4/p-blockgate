## 게이트 상세

| 게이트 | Claude가 보여줄 것 | 승인으로 인정되는 것 | 기록 |
|---|---|---|---|
| G1 | 방안 비교표(장단점, 난이도, 영향 범위, 추천) | 방안 번호 선택 또는 "추천안으로" | 이슈 본문 "선택된 방안" |
| G2 | 설계 문서 요약(AC, 기대값, 테스트 리스트) | "승인", "진행해" 등 명시적 동의 | 이슈 코멘트 "G2 승인" |
| G3 | 배포 완료 알림 + 플레이 포인트 | "좋아/승인/닫아도 돼" | 이슈 코멘트 "G3 승인" |

- 모호한 답("음 괜찮은 듯?")은 확인 질문을 한 번 더 한다.
- G3에서 피드백이 오면 피드백을 이슈 코멘트로 정리하고, 수정 범위가 AC를 바꾸면 G2부터 다시 진행한다.

## 작업 단위 원칙

| 원칙 | 내용 |
|---|---|
| 한 이슈 = 한 목적 | 이슈 하나에 기능 하나. 커지면 이슈를 나눈다 |
| 한 번에 한 이슈 (WIP) | 개발자 1명당 In Progress 이슈 1개 |
| 작은 PR | 한 PR은 리뷰 가능한 크기로. 테스트 리스트가 15개를 넘으면 이슈 분할을 제안 |
| 배포 = 플레이 가능 | main에 머지되면 바로 서버에 반영되므로, 미완성 기능은 설정 플래그로 숨긴다 |

## 동시 작업 (여러 개발자)

| 상황 | 처리 |
|---|---|
| 같은 파일을 여러 브랜치가 수정 | PR 전 `git fetch && git rebase origin/main`, 충돌은 Claude가 해결하고 테스트 재실행 |
| 동시에 머지되어 배포 경합 | `cd-server` concurrency 그룹이 순서대로 배포 |
| DB 마이그레이션 충돌 | Flyway 버전 번호가 겹치면 나중 PR이 번호를 올린다 (`db-migration` 라벨) |
