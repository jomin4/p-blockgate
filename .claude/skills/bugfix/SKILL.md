# 버그 수정 흐름

## 1. 정보 수집
| 항목 | 질문·확인 |
|---|---|
| 재현 절차 | 언제, 어떤 명령·행동을 했나 |
| 기대 / 실제 | 원래 어떻게 돼야 하고, 실제로는 어땠나 |
| 빈도 | 항상 / 가끔 |
| 로그 | 운영 로그는 **읽기만**: Tailscale SSH → `docker compose -p blockgate-prod logs --tail 200 mc` |

## 2. 이슈
`issue-create` 스킬, bug 템플릿. 우선순위: 서버 크래시·데이터 손상·접속 불가 = **P0**, 기능 오동작 = P1, 사소함 = P2.

## 3. 원인 조사
- **로컬 `blockgate-dev`에서 재현**한다. 운영 서버에서 디버깅하지 않는다.
- 필요하면 `researcher` 서브에이전트 사용.
- 원인과 수정 방안을 보고한다. 단순한 버그는 한 번의 확인으로 G1+G2를 겸한다 ("이렇게 고칠게요" → 승인).
- 수정이 AC나 동작 사양을 바꾸면 설계 문서(`docs/plans/`) 갱신 + G2.

## 4. 수정 (TDD)
1. `git switch main && git pull && git switch -c fix/<이슈번호>-<slug>`, 칸반 In Progress
2. **재현 테스트 Red**: 버그와 같은 이유로 실패하는지 확인 → `test(<영역>): #<이슈번호> 재현 테스트`
3. 수정 → Green → `fix(<영역>): <내용>`
4. 같은 원인으로 생길 수 있는 인접 케이스도 테스트 추가
5. 이후 `verify` → `review` → `ship` → `playtest-close` (G3 = 제보자 확인)

## P0 (긴급)
- 바로 개발자들에게 알리고 다른 작업보다 먼저 처리한다.
- 자동 롤백이 아직 없으므로, 직전 정상 버전으로 되돌리는 것이 빠르면 **revert PR**(`revert(<영역>): ...`)을 먼저 제안한다.
